# Quiz creation application contract

Assessment owns `QuizCreationService`, `QuizCreation` and the returned `CreatedQuiz(quizId, activityId)`. The command contains full settings and optional/initial `QuestionCreateRequest` records with their options; it is not a PATCH DTO. No JPA entities or repositories cross this application boundary.

`createForActivity(activityId, actorId, command)` requires an existing Spring transaction (`MANDATORY`). LMS-4 creates and flushes the real canonical Activity in that same transaction, then calls this bean through its Spring proxy (`createFromRequest` for HTTP embedded payloads or `createForActivity` for typed callers). The Activity must be QUIZ, the actor its owning active Tutor, and no Quiz may already exist. The command defaults `attemptsAllowed` to `1` and `gradingMethod` to `HIGHEST`; positive time limit and future deadline are required. Quiz audit fields are initialized explicitly.

### Initial questions vs. `HIDDEN` draft creation (contract reconciliation)

- **Implemented behavior:**
  - Creating a `PUBLISHED` Quiz (explicit `status: "PUBLISHED"` or omitted default `PUBLISHED`) requires at least one valid initial question and valid options; omitting or passing an empty `questions` array fails with `409 ASSESSMENT_CONFIGURATION_MISMATCH` and rolls back the `Activity`.
  - Creating a `HIDDEN` Quiz draft permits omitting or passing an empty `questions` array so Tutors can save Quiz settings first and add/edit/delete questions on `/activities/{activityId}/questions` and `/questions/{questionId}` before publishing.
  - Whenever initial `questions` are supplied (for either `HIDDEN` or `PUBLISHED`), every question and option uses the existing owner validation (including representable `NUMERIC(10,2)` points, unique `order_index`, and Adaptive Learning `skill_topic_ids` synchronization).
- **Contract assumption & DOC-05 verification status:** The standalone approved `DOC-05` specification is not present in this repository and therefore could not be directly verified here. The original pre-integration LMS-5 contract note stated that initial questions were mandatory on all `createForActivity` calls; however, the merged FE-6 Tutor authoring flow (`TutorQuizPage` creates a `HIDDEN` Quiz before adding questions), `QuizQuestionService.deleteQuestion` (permits 0 questions while `HIDDEN`, rejects deleting the last question while `PUBLISHED`), and `NotificationDeliveryRepository` (delivers `CONTENT_RELEASED` only for `PUBLISHED` Quizzes with ≥1 question) all operate under the assumption that empty `questions` are valid for `HIDDEN` drafts and forbidden for `PUBLISHED` Quizzes. If the external approved `DOC-05` requires non-empty initial questions even for `HIDDEN` Quiz creation, that requirement must be explicitly confirmed by the coordinator before modifying the create-flow contract.

The lock order is canonical Class, Quiz, then Question/Attempt/answer rows. Scope queries return IDs without preloading mutable children. Caller orchestration must obey this order too. A parent flush is not a commit. Creation failures propagate and mark the transaction for rollback; callers must never turn them into a successful Activity-only response. Validation uses `400 VALIDATION_ERROR` for settings/payload shape and the existing `400 INVALID_QUESTION` for invalid nested questions; type/configuration mismatches use `409 ASSESSMENT_CONFIGURATION_MISMATCH`. The outer HTTP create mapping retains DOC-05's error envelope.

`requirePublishable(activityId, actorId)` participates in the existing transaction and validates the actual Quiz and full question/option graph under the same lock order. It never changes Activity visibility. `ChapterService.updateActivity` now invokes `requirePublishable(activityId, tutorId)` under the Class lock on every `HIDDEN -> PUBLISHED` transition for a `QUIZ` Activity, blocking publication with `409 ASSESSMENT_CONFIGURATION_MISMATCH` until at least one valid question exists and emitting `CONTENT_RELEASED` only after valid publication.

The public command is a Java application command, not a directly exposed HTTP route. `ChapterService.createActivity` delegates `activity_type: "QUIZ"` atomically to `QuizCreationService.createFromRequest`, mapping the snake_case embedded `quiz` payload with strict integer/timestamp/decimal/question parsing, preserving all initial questions/options, and deriving actor identity from authentication. Bare `QUIZ` activities without `"quiz"` or with opposite assessment configuration keys fail with `409 ASSESSMENT_CONFIGURATION_MISMATCH`; unknown top-level keys fail with `400 VALIDATION_ERROR`. Existing assessment HTTP integer fields have local strict deserializers; global Jackson behavior is unchanged.

`GET /api/v1/activities/{activityId}/quiz` returns `activity_id` alongside Quiz settings and includes the persisted ordered `questions` array (with `options` and `is_correct`) exclusively for the owning active `TUTOR`. Student reads omit `questions` (`null` with `@JsonInclude(NON_NULL)`) so answer keys are never exposed.

Cross-owner opposite-configuration checks reject `"assignment"` on `QUIZ` and `"quiz"` on `ASSIGNMENT` with `409 ASSESSMENT_CONFIGURATION_MISMATCH`. Nonempty `skill_topic_ids` on initial or added questions participate in the approved LMS-8 workflow.

User mutation eligibility is checked after the Class lock, synchronizing archive/membership changes with start/save/clear/submit. Existing historical read and background grading/expiry policy is retained; H01 remains a coordinator clarification rather than a silent history-policy rewrite.

Historical baseline note: LMS-4 V5 became canonical after PR #30 merged, and LMS-5 added `V6__create_assessments.sql` (checksum `-1763291091`), protected alongside earlier pins by `MigrationPolicyTest`. No migration SQL was changed by the LMS-4/LMS-5 HTTP integration wiring.
